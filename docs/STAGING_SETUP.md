# Изолированная staging-сборка

Проверяемый игровой код: `3a08c3dbd8e815876f0f27baa639bc2b7055d4a4`. Подготовка не создаёт сайт, не обращается к production и не меняет Git-настройки.

## Подготовка

Из корня репозитория:

```sh
python tools/prepare_staging.py --source 3a08c3d --output work/staging-owner
python tools/serve_staging.py --directory work/staging-owner/site --port 8080
```

Локально открыть `http://127.0.0.1:8080/`. Каталог назначения должен быть новым: упаковщик отказывается заменять готовую сборку. Остановить сервер сочетанием Ctrl+C.

Результат: `site/` с 10 публичными файлами, ZIP для статического хостинга и отдельный манифест SHA-256. Включены семь глав, `saves.html` и два скрипта сохранений. Изображения уже встроены в главы. Никаких `node_modules` и сборки JavaScript не требуется.

В сайт и ZIP не попадают `.git`, `work/`, профили браузера, экспорты прогресса, отчёты, секреты и настройки среды. Применяются allowlist и проверка характерных маркеров ключей; это не замена полноценному аудиту любых будущих файлов. Сервер не выдаёт служебные пути и листинг каталога.

## Требования для удалённого тестирования

- Отдельный staging-проект или поддомен с HTTPS, без изменения production-домена.
- Статический корень — только `site/`. Сохраняются имена всех HTML-файлов и query-параметры. Отсутствующие JS должны отдавать 404, а не подменяться `index.html`.
- Корректные MIME для HTML/JS; отсутствие вмешательства, удаляющего inline-скрипты, стили и `data:image`. При CSP учесть эти существующие ресурсы отдельно.
- На период проверки желательно отключить долгий кэш HTML/JS. Выбор CDN и политику доступа утверждает владелец.
- Сайт сам не реализует авторизацию: приватный доступ обеспечивает хостинг. Владелец выбирает, кому доступна ссылка.
- Не копировать пользовательские выгрузки и данные браузера в корень публикации. После размещения проверить каждый URL и импорт только тестовых данных.

`localhost` внутри облачной среды не является ссылкой для телефона. Обычный LAN-адрес `http://192.168...` также не является подходящей заменой HTTPS: `crypto.randomUUID()` требует безопасного контекста. Для собственного TLS-сервера инструмент поддерживает `--certfile` и `--keyfile`; сертификат должен быть доверенным на телефоне, ключи нельзя коммитить или класть в `site/`. Новые сертификаты и настройки сети автоматически не создавались.

## Почему удалённый URL не выдан

Доступные операции Sites `deploy_site_version`, `deploy_private_site_version` и `save_version_and_deploy_private` прямо определяют deployment URL как production URL. Операции отдельного preview-деплоя или поддерживаемого туннеля в этой сессии нет. Подменять staging постоянной production-публикацией вопреки заданию нельзя.

Никакие сайты не создавались, credentials не запрашивались, доступы и настройки репозитория не менялись. Для удалённой ссылки владелец должен выбрать настоящий preview/staging-сервис и согласовать его подключение, либо отдельно разрешить постоянную приватную публикацию нового изолированного сайта в Sites. Это решение не принято за владельца.

После согласования нужно разместить только проверенную сборку, записать фактический URL и выполнить smoke-проверку уже на этом HTTPS origin. До того локальные измерения и проверки не подтверждают работу конкретного внешнего хостинга.
